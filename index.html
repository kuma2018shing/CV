01 — About

Research first, code second.

I'm a self-taught developer working at the intersection of code and markets. Most of what I do is not writing trading logic — it's building the apparatus that tells me whether a piece of trading logic actually does anything.

That means pulling multi-year price and order-flow history from exchange APIs, resampling it into something reproducible, and then testing an idea properly: against a matched control drawn from the same regime, split into separate training and out-of-sample periods, with the sample size and the cost assumptions stated up front.

I've run tens of thousands of events through that process. The honest headline is that most ideas do not survive it — and I think being able to say so is the point. It is easy to keep tuning parameters until a backtest looks profitable. The discipline is in recognising that you've fitted noise, writing down that the hypothesis failed, and not quietly running the search again.

What did survive that process were a handful of monotonic relationships that held in both the training and test windows, and one filter that got stronger out of sample rather than weaker. Those are the only kind of results I trust.

Away from the terminal I'm competitive at hot wings. Ghost peppers and Carolina Reapers are a normal snack.

02 — Capabilities

What I actually do.

Grouped by the part of the problem, not by the logo on the tool.

Quantitative research

Hypothesis testing on financial time series. Matched controls so you measure the effect and not the market's own drift. Train/test splits with a held-out period that never informs the design. Awareness of multiple comparisons — if you test fifty variations, some will look good by chance, and the honest move is to say so.

  • Hypothesis testing
  • Matched controls
  • Out-of-sample validation
  • Backtesting
  • Cost modelling
  • Drawdown / MAE analysis

Data engineering

Ingesting years of OHLCV and order-flow data from exchange REST APIs, handling rate limits, pagination and gaps. Caching and local persistence so a study is reproducible rather than re-downloaded. Resampling across timeframes, and the session and timezone handling that time-series work quietly lives or dies on.

  • Python
  • pandas
  • NumPy
  • REST APIs
  • Time-series resampling
  • SQL
  • Caching / persistence

Systems & automation

Turning a study into something that runs on its own: scheduled scanners across hundreds of instruments, alerting into chat platforms, state that survives a restart, and command-line tooling that removes the manual steps. Plus the ordinary software engineering underneath — version control, structured logging, packaging.

  • Scheduled jobs
  • Alerting pipelines
  • CLI tooling
  • Git / GitHub
  • Java
  • JavaScript

Market microstructure

Working knowledge of the mechanics the data actually describes: volume profiles and value area, cumulative volume delta, relative volume normalised by session, volatility regimes, and trend versus range classification. Indicator development in Pine Script alongside the Python research.

  • Volume profile
  • Order flow / CVD
  • Volatility regimes
  • Pine Script
  • Signal design
